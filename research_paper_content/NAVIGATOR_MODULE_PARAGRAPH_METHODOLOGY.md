# Navigator Module: Paragraph-Based Working Methodology

The Navigator Module serves as the foundational code parsing and analysis component within the documentation pipeline, responsible for transforming raw source code from multiple programming languages—Python, JavaScript, TypeScript, and Java—into a unified, structured intermediate representation called the Intermediate Repository (IR). Operating through a sophisticated multi-pass pipeline, the Navigator consists of four major processing phases: file scanning and language detection, component extraction via abstract syntax tree parsing using Tree-sitter, dependency resolution across the entire codebase, and dependency abstraction and consolidation for documentation purposes. The ultimate output is a complete mapping of all code components including classes, functions, methods, and variables, along with their full dependency graphs, control flow characteristics, and semantic metadata. This structured representation enables downstream agents to understand code relationships without requiring language-specific knowledge.

The Navigator's core design follows a language-agnostic architecture philosophy where language-specific parsing details are encapsulated within pluggable adapter classes, while the central parsing orchestration, dependency resolution, and graph analysis remain entirely language-independent. This architectural choice is significant because it enables the system to support new languages like Rust, Go, or C++ without requiring modifications to the core pipeline—only by implementing a new language adapter. The architecture distributes responsibility across five major layers: the file scanner and discovery layer recursively walks the repository structure identifying source files by extension; the language adapter registration layer maintains a registry of available adapters, each implementing a common interface; the Tree-Sitter parsing infrastructure layer provides robust language-agnostic parsing capabilities; the language-specific adapters layer encapsulates implementation details for each language; and finally the dependency graph construction and analysis layer builds the complete dependency models.

All code entities throughout the system are represented using the unified CodeComponent dataclass, which captures language-agnostic structural and semantic information including a unique identifier (such as "src.utils.math:add"), a human-readable name, a component type drawn from a consistent hierarchy, the source language, location information including file path and line ranges, the complete source code text, function signatures, existing docstrings if present, parameter information with type hints, return type annotations, cyclomatic complexity measurements, physical line counts, a set of component IDs representing dependencies, control flow characteristics such as async operations and exception handling patterns, visibility flags for public or private status, import information for external retrieval, and language-specific metadata. This unified model is extraordinarily powerful because it allows downstream Reader, Searcher, and Writer agents to operate identically across Python, JavaScript, Java, and TypeScript without any language-specific conditional logic. A Python class, JavaScript class, Java class, and TypeScript class all become the same ComponentType.CLASS in the unified representation.

The Navigator's workflow begins with file discovery where it creates an AdapterRegistry containing instances of all supported language adapters, then walks the entire repository directory tree recursively, examining each file's extension against the registered adapters' extension lists. When a matching adapter is found, the file's contents are read with UTF-8 encoding and error-tolerance for robustness, then routed to the matched adapter. Files without matching adapters are silently skipped, gracefully handling mixed repositories containing configuration files, documentation, and other non-code files. This design choice prevents the Navigator from failing on heterogeneous repositories, which is essential for real-world usage.

In the component extraction phase, each language adapter independently extracts components from its assigned files through a standardized process beginning with parse tree generation. Most languages use Tree-sitter to convert source code into a parse tree, a representation that captures the complete syntactic structure as nested nodes. For Python, when Tree-sitter is unavailable, the system falls back to Python's native AST parser, ensuring robust operation even in degraded conditions. The adapters then traverse their parse trees recursively, identifying specific node types that represent code entities: in Python these include ClassDef nodes for classes, FunctionDef nodes for functions or methods distinguished by parent context, and module-level assignments for global variables; in JavaScript and TypeScript, ClassDeclaration nodes become classes, FunctionDeclaration nodes become functions, ArrowFunction nodes are captured as a specific function type, and top-level VariableDeclarations become global variables; in Java, ClassDeclaration nodes become classes, MethodDeclaration nodes become methods, and class-level FieldDeclarations become class variables.

For each identified component, the adapters extract comprehensive metadata including start and end line numbers from the parse tree, the complete function or method declaration statement as the signature, the first string literal in the function body as the docstring if present, parameter names and type hints from the declaration, return type annotations if available, visibility information detected using language conventions such as leading underscores in Python indicating private members, decorator metadata including information for API endpoint detection and async detection, and initial control flow characteristics recording the presence of async/await operations, loops, branches, and exceptions. The file path is simultaneously converted to a module path by computing the relative path from the repository root, replacing directory separators with dots, and removing the file extension—for example, `src/utils/math.py` becomes `src.utils.math`. Component IDs are then constructed as `{module_path}:{component_name}`, enabling later lookup. As each file is processed, its components are aggregated into a unified `all_components` dictionary that maps component IDs to CodeComponent objects, representing all code components extracted across the entire repository and enabling O(1) lookup during subsequent dependency resolution.

The dependency resolution phase represents the second pass over the codebase, where each language adapter analyzes individual components to determine their dependencies. A component A depends on component B when one of several specific conditions is satisfied: A directly calls a function or method provided by B, A declares a variable with a type defined in B, A creates an instance of a class defined in B, A's class inherits from B's class, A accesses an attribute or property of B, or A explicitly imports from module B. Each language adapter scans the component's source code for patterns indicating these relationships, typically using a combination of regex-based pattern matching for simpler cases and AST traversal for complex scenarios. For direct calls, the system searches for function names followed by parentheses; for type annotations, it looks for variable declarations with type specifications; for imports, it identifies import statements and extracts the imported items; for object and array method access, it tracks method call chains through objects.

For each detected dependency, the adapter attempts resolution against the `all_components` dictionary: it first performs a direct lookup by name, and if that succeeds, it identifies the component; if direct lookup fails, it applies heuristics such as inferring the owner class from method call context, searching for module names in imports, or searching for classes matching type names. As dependencies are added to each component's `depends_on` set, duplicates are automatically eliminated because sets inherently prevent duplicate entries. This phase represents O(C × D) complexity where C is the total number of components and D is the average number of dependency references per component.

Following raw dependency extraction, the Navigator applies a critical phase of semantic abstraction via the `apply_doc_dependency_rules()` function to transform low-level dependencies into documentation-oriented abstractions suitable for high-level documentation purposes. The first abstraction rule directs that classes should depend on classes, not on individual methods—when documenting ClassA, readers care that ClassA uses ClassB and would look up ClassB to understand ClassA's behavior, rather than needing to know which specific internal methods are called. The second rule specifies that methods should depend on classes, not other methods, transforming method-level granularity to class-level granularity because the class-level dependency is semantically more important. The third rule eliminates self-references: components should not depend on themselves, and methods are conceptually part of their containing class rather than external dependencies. The fourth rule preserves global variable dependencies as explicit entries because global variables represent shared mutable state that documentation must explain clearly. A fifth optional rule may hide private helper method calls within the same class, treating implementation details as implicit in the class-level dependency.

These abstraction rules operate through sequential passes over all components, updating `depends_on` sets with each pass to reflect increasingly abstract documentation-oriented relationships. The transformation is crucial because the raw dependencies extracted from source code analysis operate at implementation level, showing every single method call and attribute access, while documentation readers need higher-level abstractions showing what major components a piece of code depends on. This abstraction bridges the gap between syntactic code structure and semantic documentation structure.

From the abstracted dependencies, the Navigator constructs a directed acyclic graph (DAG) using the `build_graph_from_components()` function, where nodes represent components and directed edges A → B represent dependency relationships: A depends on B. The graph is represented internally as an adjacency list enabling O(1) neighbor lookups and supporting efficient graph algorithms. The Navigator applies Tarjan's Strongly Connected Components algorithm to detect cycles: real-world code sometimes contains circular dependencies where A depends on B and B depends on A, such as in Python with circular imports or in JavaScript with module systems. The algorithm identifies all strongly connected components (groups of nodes that depend on each other), reports those with multiple nodes as cycles, and can optionally apply resolution strategies such as removing lowest-priority edges or collapsing circular components to module level. Currently, the Navigator detects and logs cycles but permits them in the final graph, allowing the documentation pipeline to be aware of circular relationships without failure.

The component type hierarchy recognized consistently across all languages includes CLASS for class or record definitions, FUNCTION for top-level functions, METHOD for functions within classes, ARROW_FUNCTION for concise function syntax in JavaScript and TypeScript, ASYNC_FUNCTION for async function variants, VARIABLE for local variables, GLOBAL_VARIABLE for module-level variables, CLASS_VARIABLE for variables within classes, INTERFACE for interfaces or protocols in Java and TypeScript, ENUM for enumeration definitions, MODULE for modules or namespaces, and OTHER for unclassified components. This hierarchy is mapped consistently across languages so that a Python class, JavaScript class, Java class, and TypeScript class all map to the same ComponentType.CLASS, enabling polymorphic downstream processing.

Each language adapter implements three critical methods on the BaseLanguageAdapter interface. The `parse()` method converts source code to a parse tree using the language's parser—for Python this uses the Tree-sitter parser when available with automatic fallback to Python's native AST module, while for JavaScript, TypeScript, and Java it uses Tree-sitter consistently. The `extract_components()` method traverses the parse tree to identify components and extract metadata, returning a list of CodeComponent objects or a dictionary mapping IDs to components; implementation patterns vary by language but consistently look for specific node types (class declarations, function declarations, variable assignments) and extract associated metadata like location, signature, docstring, parameters, and visibility. The `resolve_dependencies()` method analyzes a single component's source code to identify dependencies, returning a set of component IDs; this typically involves scanning source code for function calls, imports, type hints, attribute access, and class instantiation, then resolving detected names to component IDs using the all_components lookup dictionary.

To illustrate the complete pipeline concretely, consider parsing a Python file: first, during file discovery, the .py extension causes the file to be routed to PythonAdapter; during component extraction, the parse tree is analyzed to identify an APIHandler class with __init__ and create_user methods, each extracted as separate CodeComponent objects with their location, signature, docstring, and metadata; during dependency resolution, the type annotation `db: Database` in the create_user method reveals a dependency on the Database class, while the call `validator.validate()` reveals a dependency on ValidateUser, and the call `self.db.save()` reveals another Database dependency. During the abstraction phase, method-level dependencies are promoted to class level, and final output shows the APIHandler class depending on the Database class, with create_user method depending on both ValidateUser and Database. This transformed dependency structure is more suitable for documentation than the raw syntactic dependencies.

The Navigator's computational complexity is favorable for large codebases: file walking is O(F) where F is total files, parsing is O(L) where L is total lines across all files (Tree-sitter is linear), dependency resolution is O(C × D) where C is components and D is average dependency references, and final abstraction and graph construction is O(C + E) where E is total dependencies. For a typical codebase with 10,000 files averaging 100 lines each and approximately 50,000 components, parsing completes in O(1,000,000) operations and dependency resolution in O(100,000) operations—both linear in source size and completing in seconds to minutes on modern hardware. No exponential or factorial operations exist, making the system highly scalable to enormous codebases.

The Navigator's final output is a complete CodeComponent repository consisting of an `all_components` dictionary mapping component IDs to CodeComponent objects containing complete metadata, structural information, and control flow characteristics; a `dependency_graph` dictionary mapping component IDs to sets of component IDs representing their dependencies; and optional IR exports to disk for persistence and external tool integration. This IR serves as the foundation for all downstream agents: the Reader Agent consumes CodeComponent objects to assess complexity and determine information needs, the Searcher Agent uses component_map and dependency_graph to retrieve context for documentation, the Writer Agent uses component source code and metadata to generate documentation, and the Verifier Agent uses component type and complexity to calibrate quality expectations. Navigator accuracy is critical—errors in component extraction or dependency resolution propagate through all subsequent pipeline stages.

The Navigator implements several defensive strategies ensuring robust operation despite real-world code complexity and edge cases. File encoding tolerance using UTF-8 with error-ignore handling skips unparseable bytes rather than crashing. Adapter fallbacks ensure Python can use native AST when Tree-sitter is unavailable. Silent unsupported file skipping allows mixed repositories without problems. Dependency resolution graceful degradation skips unknown dependencies rather than failing. Component normalization handles adapters returning different formats. Circular dependency tolerance detects and logs circular relationships without failing. These defensive implements prevent single parsing errors from cascading through the entire system.

The Navigator Module contributes fundamentally to the documentation pipeline through language-agnostic parsing supporting multiple languages via pluggable adapters, complete code extraction identifying all code entities across the repository, accurate dependency resolution mapping code relationships, semantic abstraction transforming low-level dependencies to documentation-oriented abstractions, robust parsing handling edge cases and encoding issues gracefully, and unified code representation enabling polymorphic downstream processing. These contributions establish the Navigator as the reliable foundation upon which the entire automated documentation system is built. By accurately identifying all code components and their relationships while abstracting implementation details to focus on documentation-relevant semantics, the Navigator enables Reader, Searcher, and Writer agents to generate high-quality documentation seamlessly across Python, JavaScript, TypeScript, and Java codebases without requiring language-specific logic in downstream components.
